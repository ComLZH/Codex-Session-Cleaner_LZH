# Codex 对话清理工具通用化与控制台集成方案规划

**文档版本**：v2.1.1-Planning-Review  
**创建时间**：2026-09-03  
**最近调整时间**：2026-09-03  
**状态**：方案修订阶段（待用户复审，未进入实施）  
**面向目标**：将现有清理工具升级为通用化、菜单交互式、默认只读、删除操作可审计且可恢复的统一 Windows 控制台程序。

## 1. 背景、目标与边界

### 1.1 现状痛点

1. **目标硬编码**：现有 `codex_manual_cleanup.py` 与 `codex_sidebar_ghost_cleanup.py` 分别依赖固定项目配置和固定 Thread ID，处理新对象时需要手工修改 JSON。
2. **入口分散**：根目录存在 6 个 `.cmd` 与 2 个 `.ps1`，使用者需要理解“整项目清理”和“侧边栏幽灵修复”的差异。
3. **运行环境绑定**：现有启动脚本优先使用固定 Anaconda 路径，迁移到其他电脑时不够稳定。
4. **扫描与删除耦合不清**：当前方案主要通过“检测到 Codex 后拒绝执行”保护写操作，但缺少统一的只读浏览、Dry-run、版本兼容门禁和崩溃恢复机制。
5. **内部存储持续演进**：当前已知环境同时存在两套 `state_5.sqlite`、两套 `logs_2.sqlite` 及多个 SQLite sidecar，且不同状态库的表结构和职责并不完全相同。

### 1.2 改造核心目标

* **【单一主入口】**：提供统一的双击控制台入口 `Codex会话管理与清理工具.cmd`。
* **【默认只读】**：Codex 运行时允许浏览和审计；只有进入删除阶段才要求 Codex 完全退出。
* **【动态扫描与证据分类】**：扫描当前用户选定的 `.codex` 数据根，通过多源证据而不是单一字段判断会话状态。
* **【安全选择与 Dry-run】**：支持项目筛选、序号多选、区间选择和 Thread ID 输入，但正式删除前必须生成精确的执行计划。
* **【删除级进程守门】**：删除前执行正常退出检查、有界轮询、独占性验证、WAL 状态检查和二次扫描。
* **【无第三方 Python 包依赖】**：核心功能仅使用 Python 标准库；Python 运行时本身仍属于前置依赖。
* **【可审计、可恢复】**：执行前构建完整修改集合并备份；物理文件先隔离；跨数据库操作通过操作日志与补偿恢复保证可恢复性。
* **【失败关闭】**：遇到未知数据库版本、未知表结构、路径归属不明、锁状态不明或备份不完整时，只允许审计。

### 1.3 明确范围

1. 本工具只处理**当前 Windows 用户、当前选定 `.codex` 数据根**，不宣称覆盖全机所有用户。
2. 本工具只能验证本机记录，不能证明 OpenAI 服务端、其他主机或其他账户中的副本已经物理删除。
3. 云端目录项只读展示；显式 Thread ID 删除也必须证明目标属于本机 `host_id='local'`。
4. 本工具永远不得进入项目源码目录删除源码文件。
5. 首期不默认提供以下高风险能力：
   * 强制结束 Codex 进程树；
   * 永久删除孤立 rollout；
   * 删除 Automation 本体；
   * 修改 `config.toml` 信任声明；
   * 整项目彻底清理。
6. 上述高风险能力只有在独立设计、独立确认和专项测试完成后才能分阶段启用。

### 1.4 设计原则

* **读写分离**：启动、浏览、筛选和健康检查不要求退出 Codex；删除前必须重新进入独占流程。
* **证据优先**：状态标签必须附带来源、时间和置信度。
* **精确匹配**：数据库使用参数化 SQL；项目路径按完整目录边界匹配，禁止子串匹配。
* **最小修改**：只处理执行计划中明确列出的对象，不对未知表做全文模糊删除。
* **恢复优先**：没有完整备份、隔离区和恢复验证就不得开始删除。
* **版本门禁**：内部结构变化时默认停止写入，先增加对应版本适配器。
* **隐私最小化**：报告不得保存会话正文、Automation 提示词或不必要的账户信息。

## 2. 总体架构与运行流程

```text
+-------------------------------------------------------------------------------+
|                    Codex会话管理与清理工具.cmd                                  |
+---------------------------------------+---------------------------------------+
                                        | 探测并验证 Python
                                        v

|  - 枚举数据库、WAL/SHM、JSON、JSONL、锁和物理会话文件                           |

                                        |

|  - 以 (host_id, thread_id) 与 thread_id 建立证据集合                            |
|  - 输出互斥状态、依据、时间和置信度                                             |
+---------------------------------------+---------------------------------------+
                                        |

+-------------------------------------------------------------------------------+

|  - Codex 运行时也可浏览，但结果标记为可能变化                                   |
|  - 序号绑定 scan_id + thread_id，不能仅保存菜单序号                             |
|  - 输出精确修改集合、关联对象、备份大小与阻断原因                               |
+---------------------------------------+---------------------------------------+
                                        | 用户请求删除
                                        v
+-------------------------------------------------------------------------------+

|  - 受检 checkpoint、quick_check、重新扫描并比对目标指纹                         |
|  - 目标发生变化时废弃旧计划并要求重新确认                                       |
+---------------------------------------+---------------------------------------+
                                        |
                                        v
+-------------------------------------------------------------------------------+
```

关键原则：本方案不再使用“事务级级联清理”描述整个操作，因为多个 SQLite 文件、普通文件和目录之间无法组成同一个原子事务。

## 3. 核心模块设计

### 3.1 启动包装器与 Python 探测

新增 `run_unified_console.ps1`，建议采用以下受控探测顺序：

1. 工具配置中由用户明确指定且存在的 Python 路径。
2. Windows `py.exe -3` 启动器。
3. PATH 中的 `python.exe` 或 `python3.exe`。
4. 当前用户 Codex 缓存运行时，作为尽力而为的回退：
   `$env:USERPROFILE\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`
5. 不自动遍历和执行任意 Anaconda/Miniconda 环境中的 Python。

每个候选解释器必须实际执行能力探测并满足：

* Python 版本 `>= 3.10`；
* 可导入 `sqlite3`、`ctypes`、`json`、`hashlib`、`pathlib`；
* `sqlite3.sqlite_version` 满足工具支持基线；
* 能正确输出 UTF-8；
* 返回值和异常能够传回 `.cmd`。

“零外部依赖”统一改称“无第三方 Python 包依赖”。如果以后需要真正免安装，再另行评估签名的单文件可执行版本。

### 3.2 存储发现、清单与版本门禁

#### 3.2.1 当前已知存储基线

扫描器至少识别以下位置，但不能假设它们一定全部存在：

| 类型 | 已知路径或对象 |
| :--- | :--- |
| 主状态库 | `.codex/state_5.sqlite` |
| 兼容/历史状态库 | `.codex/sqlite/state_5.sqlite` |
| 主日志库 | `.codex/logs_2.sqlite` |
| 兼容/历史日志库 | `.codex/sqlite/logs_2.sqlite` |
| 历史投影库 | `.codex/thread_history_1.sqlite` |
| 桌面目录库 | `.codex/sqlite/codex-dev.db` |
| 辅助数据库 | `goals_1.sqlite`、`memories_1.sqlite`、`queue_1.sqlite` 及对应兼容路径 |
| 文本状态 | `.codex-global-state.json`、其应用备份、`session_index.jsonl`、`cap_sid` |
| 物理会话数据 | `.codex/sessions` 下的 rollout JSONL |
| 运行与可视化数据 | `thread-writer-locks`、`visualizations` |
| 项目信任配置 | `config.toml`，首期只读 |

所有 SQLite 文件都必须同时清点可能存在的 `-wal` 与 `-shm`，不能只列主数据库文件。

#### 3.2.2 结构指纹

对每个数据库记录：

* 文件路径、大小、修改时间和 journal mode；
* `_sqlx_migrations` 或 `codex_schema_migrations` 版本；
* 必需表、列、主键、索引和外键；
* 适配器名称与支持级别；
* 是否存在未知但包含 `thread_id`、`assigned_thread_id`、`target_thread_id` 或项目引用的表。

当前已知需要纳入适配器评估的对象包括但不限于：

* `thread_artifacts`；
* `thread_dynamic_tools`；
* `thread_spawn_edges`；
* `agent_job_items.assigned_thread_id`；
* `local_thread_catalog_scan_entries`；
* `automation_runs`、`automations`、`inbox_items`；
* `thread_realtime_items`。

若结构指纹不匹配，工具必须显示差异并降级为只读，禁止采用“缺表则跳过”的最佳努力写入方式。

#### 3.2.3 只读连接与瞬时锁防御

Codex 运行时的扫描连接统一通过专用 `connect_readonly()` 建立，最低要求为：

```python
conn = sqlite3.connect(database_path.as_uri() + "?mode=ro", uri=True, timeout=5.0)
conn.execute("PRAGMA busy_timeout = 5000")
conn.execute("PRAGMA query_only = ON")
```

具体守则：

* `timeout=5.0` 与 `busy_timeout=5000` 提供最长约 5 秒的**有界等待**，不是非阻塞操作，也不能保证永久消除 `database is locked`。
* 扫描器必须捕获 `sqlite3.OperationalError`；锁持续超过等待时间时，将该数据库标记为 `TEMPORARILY_BUSY`，将本次扫描标记为不完整，并允许用户稍后重试，不能让整个控制台异常退出。
* 可以在总扫描时限内进行少量有界重试，但不得无限等待。总等待预算与重试次数应可测试、可配置。
* WAL 可能仍处于活动状态时不得使用 `immutable=1`，否则可能忽略尚未合并的 WAL 内容并产生错误判断。
* 每个数据库在自己的只读事务中取得一致视图，并记录连接时间；不同数据库之间仍不构成同一时刻的全局快照。
* 任何 `TEMPORARILY_BUSY`、读取超时或扫描不完整结果都禁止生成可执行的删除计划。

### 3.3 会话证据模型与互斥分类

#### 3.3.1 证据集合

以 `thread_id` 为正文关联主轴；在目录数据库中使用 `(host_id, thread_id)` 作为来源作用域。每个对象收集：

* 本地/云端 catalog 记录及 `missing_candidate`；
* 两套状态库中的线程记录、`cwd`、`project_id` 和 rollout 路径；
* 历史投影库中的 turns/items/realtime/projection 记录；
* `session_index.jsonl` 精确记录；
* rollout 是否存在、是否为普通文件、是否可解析、大小和修改时间；
* writer lock、visualization、日志和辅助引用；
* Automation、inbox、batch job、spawn edge 等关联对象；
* 最近更新时间以及 Codex 是否正在运行。

`missing_candidate` 只能作为辅助信号，不能单独授权删除。

#### 3.3.2 互斥状态

| 状态 | 核心条件 | 默认权限 |
| :--- | :--- | :--- |
| `CLOUD_READONLY` | catalog host 不是 `local`，或来源被识别为云端 | 只读 |
| `IN_USE` | Codex/相关写入进程、writer lock 或数据库占用仍存在 | 只读 |
| `HEALTHY_LOCAL` | 本地线程元数据与可读 rollout 一致，且无来源冲突 | 可手工选择 |
| `CATALOG_LAG` | 本地正文与 rollout 完整，但本地 catalog 暂未出现 | 只读观察 |
| `VERIFIED_GHOST` | 本地 catalog 残留，但状态、历史、索引、rollout 和锁均不存在；两次稳定扫描一致且满足时间阈值 | 可进入幽灵清理计划 |
| `BROKEN_BODY` | 状态、历史或索引仍存在，但 rollout 缺失、损坏或无法读取 | 只读，要求专项确认 |
| `ORPHAN_CANDIDATE` | rollout 存在，但所有受支持元数据源均无记录，且超过时间阈值 | 仅允许隔离 |
| `UNKNOWN_CONFLICT` | 来源互相矛盾、路径不明、结构未知或无法证明本地归属 | 只读 |

分类优先级必须明确：云端与活动状态优先阻断；任何证据冲突都覆盖自动清理资格。不能让同一对象同时属于“幽灵”和“正文断头”。

### 3.4 项目识别与路径安全

统一 `normalize_path()` 至少处理：

* `\\?\` 与 `\\?\UNC\` 前缀；
* Windows 大小写与分隔符；
* 盘符、UNC、尾部分隔符；
* `.`、`..`；
* 符号链接、junction 和其他 reparse point。

必须分别记录用户看到的逻辑 `.codex` 路径与通过句柄解析得到的实际物理路径。允许 `.codex` 根本身是经过验证的 Junction，但后续路径边界、卷识别和删除保护都以实际物理根为准；根目录内部出现的未知 reparse point 仍默认拒绝。

项目归属规则：

1. 优先使用经过验证的 `project_roots` 和完整 `cwd`。
2. `project_id` 允许为空，不能作为唯一依据。
3. 子目录匹配必须采用路径段边界，并记录命中的根。
4. 同时匹配多个根时，先采用最长完整根；仍有歧义则进入 `UNKNOWN_CONFLICT`。
5. worktree 默认作为独立工作根展示，除非数据库明确提供可靠关联。
6. 项目名称不能作为删除身份，仅用于显示。

删除文件前必须：

* 解析最终路径并证明位于允许的 `.codex/sessions`、`.codex/thread-writer-locks` 或 `.codex/visualizations` 子目录；
* 拒绝删除允许根本身；
* 拒绝未知 reparse point；
* 记录源对象所在的实际卷标识，而不是只根据逻辑盘符判断；
* 验证文件类型和预期命名；
* 删除前再次核对文件身份、大小和修改时间，防止扫描后的对象被替换。

### 3.5 控制台交互与 Dry-run

首期菜单建议：

```text
[1] 重新扫描当前 .codex 数据根
[2] 按项目或状态浏览本地会话
[3] 查看指定会话的完整证据
[4] 选择本地会话并生成 Dry-run
[5] 输入 Thread ID 并生成 Dry-run
[6] 执行已确认的受支持清理计划
[7] SQLite 与文本状态只读健康检查
[8] 查看或恢复未完成操作
[9] 可选数据库空间维护（仅已完成操作之后）
[0] 退出
```

交互规则：

* 菜单序号只在当前 `scan_id` 内有效，选中后立即固化为 Thread ID 集合。
* 输入解析必须去重、检查范围并拒绝非法区间。
* Thread ID 必须满足预期 UUID 格式，并再次检查本地来源。
* Dry-run 必须显示：
  * Thread ID、标题、完整项目路径和状态；
  * 每个数据库预计处理的表和行数；
  * 文本文件预计移除的精确 JSON 路径或 JSONL 行；
  * 预计隔离的物理文件；
  * Automation、inbox、job、spawn edge 等关联对象；
  * 备份位置、预计空间和阻断项；
  * `scan_id`、目标指纹和短操作码。
* 正式确认短语应包含数量和短操作码，例如：
  `确认删除3个本机会话 A7C19E2B`
* 整项目操作若未来启用，确认信息必须包含完整路径和操作码，不能只输入项目名称。

#### 3.5.1 序号选择输入规范化

序号、列表和区间输入允许常见中文输入法字符。建议先做 Unicode NFKC 规范化，再对少量仍未统一的分隔符做显式映射：

```python
import re
import unicodedata

selection = unicodedata.normalize("NFKC", raw_input)
selection = selection.translate(
    str.maketrans(
        {
            "、": ",",
            ";": ",",
            "~": "-",
            "–": "-",
            "—": "-",
        }
    )
)
selection = re.sub(r"\s+", "", selection)
```

NFKC 会同时统一常见全角数字、全角逗号、全角中划线和全角空格；额外映射覆盖顿号、分号、波浪线以及长短横线。规范化后仍必须执行严格语法校验。

输入防护要求：

* 限制原始输入长度、选择项数量和单个区间跨度，避免异常巨大输入。
* 拒绝空项、倒序区间、重复分隔符、负数、零和超出菜单范围的编号。
* 去重后保持用户首次选择顺序。
* 控制台回显规范化表达式、解析后的序号和最终 Thread ID，待用户核对。
* 此类容错规范化**仅用于序号选择语法**；永久删除确认短语和操作码仍按原值精确匹配，不能套用 NFKC 或分隔符替换，以免削弱确认防线。

### 3.6 删除级进程守门

进程守门仅在执行删除时启用：

1. 提示用户保存工作并通过 Codex 菜单和系统托盘正常退出。
2. 使用 Windows API 有界轮询进程，不使用固定 1.5 秒等待。
3. 进程识别采用受支持的精确映像名，并尽可能校验可执行路径和父进程；无法读取身份时按不安全处理。
4. 获取清理工具自身的单实例互斥锁，阻止两个清理进程同时写入。
5. 对本次修改集合中的数据库、JSON、JSONL 和目标文件重新检查占用。
6. 对每个 WAL 数据库执行受检 checkpoint，并读取 `(busy, log, checkpointed)` 返回值；`busy != 0` 或未完成时立即中止。
7. checkpoint 后运行只读 `PRAGMA quick_check`，异常时不得继续。
8. 重新扫描目标并比较 Dry-run 指纹；任何标题、来源、路径、状态或修改时间变化都使旧计划失效。

首期不提供 `taskkill /F /T`。以后如增加强制关闭，只能置于高级选项中，要求独立确认、显示精确 PID 与路径，并在访问拒绝或身份不明时停止。

### 3.7 备份、隔离与隐私

#### 3.7.1 备份位置

默认建议使用：

`%LOCALAPPDATA%\CodexCleanup\backups\<operation_id>\`

不默认写入本工具工程目录，避免备份进入 Git、桌面同步或项目打包。备份目录应限制为当前用户访问。

必须提示用户：完整 SQLite 备份可能包含未被选择的其他会话和账户元数据。报告不得包含正文；备份保留期限和删除方式必须由用户可见地配置。

这里规定的是**备份目录**。备份本来就需要复制数据，因此可以位于不同卷；物理对象的临时隔离目录另按 3.7.5 的同卷规则选择，二者不得混用。

#### 3.7.2 SQLite 一致性备份

SQLite 主数据库优先使用 Python 标准库 `sqlite3.Connection.backup()` 创建独立快照，不把 `shutil.copy2()` 复制主库、WAL 和 SHM 的组合当作默认恢复基线。

推荐流程：

1. Codex 已正常退出，修改集合中的数据库均通过占用检查。
2. 对 WAL 数据库执行受检 checkpoint；返回 busy、未完成或异常时中止。
3. 对源数据库执行 `PRAGMA quick_check`。
4. 建立专用源连接和全新目标数据库连接，调用 `source_connection.backup(target_connection)`。
5. 关闭目标连接并刷新落盘后，对快照再次执行 `PRAGMA quick_check`。
6. 计算快照 SHA-256，并在清单中记录 `backup_method=sqlite_connection_backup`、源结构指纹和目标结构指纹。
7. 任何步骤失败都删除或标记不完整的快照，并在首次业务写入前中止。

`Connection.backup()` 生成的是事务一致、可独立打开且不依赖源 WAL 的数据库快照，但不得在文档或界面中称为“100% 完美备份”：源库本身损坏、磁盘故障、目标写入失败或多个数据库之间时间点不同仍然可能造成风险。因此源库和快照都必须校验。

sidecar 处理规则：

* `-wal` 和 `-shm` 的存在性、大小、mtime 与哈希写入诊断清单。
* 在 checkpoint 已确认完成的前提下，恢复基线是经过校验的独立快照库，而不是依赖 sidecar 的文件组合。
* 恢复时必须先确认 Codex 已退出并关闭工具连接；旧主库及其现存 sidecar 先移入恢复隔离区，再以快照替换主库，避免旧 WAL 被错误重放到已恢复数据库。
* 不得把源库的 `-shm` 直接还原为运行依赖；SQLite 应在下次正常打开时自行创建需要的共享内存状态。
* 多个数据库的 `backup()` 仍是逐库快照，不构成跨库原子时间点；依靠 Codex 已退出、目标指纹和操作日志维持整体一致性。

#### 3.7.3 修改集合驱动

先生成完整 `mutation_set`，再决定备份对象。凡是可能被修改、替换、截断、删除或移动的对象，都必须有对应恢复策略，包括：

* 两套状态库和日志库；
* 历史库、目录库及实际参与写入的辅助库；
* 所有相关 SQLite 主文件与 sidecar 状态；
* `.codex-global-state.json` 及需要同步处理的应用备份；
* `session_index.jsonl`、`cap_sid`；
* 未来启用时的 `config.toml`；
* rollout、writer lock、visualization 和其他物理目标。

不得使用只复制“主库加部分 WAL”的固定清单。

#### 3.7.4 清单要求

`manifest_sha256.json` 至少包含：

* 原始绝对路径；
* 原对象是否存在、类型、大小、mtime；
* 原始 SHA-256 与备份 SHA-256；
* 备份相对路径；
* 所属修改步骤；
* 恢复策略；
* 数据库结构指纹；
* 工具版本和操作 ID。

开始前检查可用磁盘空间。任何复制、哈希或清单持久化失败都必须发生在首个写操作之前并立即中止。

#### 3.7.5 同卷隔离策略

rollout、锁和 visualization 不直接永久删除，而是移动到当前操作的隔离目录。隔离目录必须根据**每个源对象解析后的实际卷**分配，不能固定假设 `.codex` 位于 C 盘。

同卷规则：

1. 解析逻辑 `.codex` 根及每个物理目标的最终路径。
2. 使用实际卷标识判断源和隔离目录是否位于同一卷，不能只比较盘符字符串。
3. `.codex` 根是 Junction 时，优先在其实际物理父目录旁创建当前用户可写的隐藏隔离根，例如：
   `<resolved_codex_parent>\.codex-cleanup-quarantine\<operation_id>\`
4. 若目标跨越多个实际卷，则为每个卷分别建立隔离根，并在 manifest 中保存源到隔离位置的一一映射。
5. 隔离位置不得直接默认创建在 `C:\`、`D:\` 等卷根，避免权限、ACL 继承和敏感数据暴露问题。
6. 使用同卷 `os.replace()` 或等价重命名；一旦返回跨卷错误、目标冲突或占用错误，立即停止并进入补偿恢复。
7. 禁止悄悄退化为“跨卷复制后删除源文件”。如果找不到同卷且安全可写的隔离目录，本次操作必须阻断。

同卷重命名可以避免常规的跨卷复制再删除流程，但仍不能表述为绝对不会失败；目标占用、ACL、杀毒软件或底层 I/O 故障仍需由操作日志和补偿恢复处理。

只有验证成功并经过用户选择的保留期后，才允许单独清除隔离内容。

未完成或需要恢复的操作，其备份和隔离内容不得被自动清理。

### 3.8 分阶段执行与崩溃恢复

#### 3.8.1 操作状态机

每次写操作创建 `operation.json`，状态至少包括：

1. `PREPARED`
2. `BACKED_UP`
3. `DATABASES_UPDATED`
4. `TEXT_STATE_UPDATED`
5. `FILES_QUARANTINED`
6. `VERIFIED`
7. `COMPLETED`
8. `ROLLBACK_REQUIRED`
9. `ROLLED_BACK`

状态文件必须采用原子替换并强制刷新。每完成一个不可忽略的步骤就记录结果、行数和哈希。

#### 3.8.2 执行顺序

1. 固化最终 `mutation_set` 和目标指纹。
2. 创建并验证完整备份。
3. 按适配器对每个 SQLite 文件分别执行事务，提交后记录结果。
4. 按已知结构原子更新 JSON/JSONL 等文本状态。
5. 将物理目标移动到隔离区。
6. 关闭所有数据库连接。
7. 执行全量验证。
8. 验证成功后标记 `COMPLETED`；失败则标记 `ROLLBACK_REQUIRED` 并进行补偿恢复。

多个数据库和文件系统之间不存在单一原子提交。自动恢复依赖完整备份、操作日志和可重复执行的补偿步骤。

#### 3.8.3 启动恢复

工具每次启动时先查找未完成操作：

* `PREPARED` 且未写入：可安全取消。
* 已进入写入阶段：阻止新操作，只允许查看、继续验证或恢复。
* 恢复时先确认 Codex 已退出，再关闭连接、恢复数据库和文本文件、移回隔离对象。
* 恢复后重新校验备份哈希、目标哈希、SQLite 完整性和物理文件存在性。
* 恢复失败不得删除备份，应生成脱敏故障报告并要求人工处理。

### 3.9 结构感知的清理适配器

每个受支持结构版本维护明确的表、列和依赖顺序。

#### 3.9.1 线程清理

适配器需要评估并按版本处理：

* `codex-dev.db`
  * `local_thread_catalog`，必须限制 `host_id='local'`；
  * `thread_timeline_ledger`；
  * `inbox_items`；
  * `automation_runs`；
  * `local_thread_catalog_scan_entries` 等同步状态表。
* `state_5.sqlite`
  * `threads`；
  * `thread_spawn_edges`；
  * `thread_artifacts`；
  * `thread_dynamic_tools`；
  * `agent_job_items.assigned_thread_id` 等版本相关引用。
* `thread_history_1.sqlite`
  * `thread_turns`；
  * `thread_items`；
  * `thread_realtime_items`；
  * `thread_history_projection_state`。
* `logs_2.sqlite`
  * 首选精确 `thread_id`；
  * 路径或正文模糊匹配只能用于只读提示，不得直接作为删除条件。
* 文本状态
  * `session_index.jsonl` 逐行解析，按结构化 Thread ID 精确过滤；
  * `.codex-global-state.json` 只允许按已知 JSON 路径修改并展示前后差异；
  * 不使用“递归删除任意包含 ID 的键或字符串”的泛化算法。

#### 3.9.2 Automation 与 Job

* 清理会话时如发现 Automation 本体指向目标线程，默认阻断并要求用户独立选择。
* 删除 Automation 运行记录不代表可以自动删除 Automation 配置。
* Batch/agent job 引用必须展示；如何解除引用由对应结构适配器明确规定。
* 无法确认语义时进入 `UNKNOWN_CONFLICT`。

#### 3.9.3 项目级清理

项目级清理推迟到第三阶段实施，并额外要求：

* 列出该项目下全部本地线程和所有匹配根；
* 证明项目记录未被其他根或未选线程共享；
* 项目表删除与线程删除分别展示；
* 完整路径加操作码确认；
* 明确声明项目源码不会被删除；
* `config.toml` 信任声明作为独立选项，不与项目清理默认绑定。

### 3.10 校验与后置维护

#### 3.10.1 删除前校验

* 所有目标均为本地、受支持、非活动状态；
* 所有数据库 `quick_check == 'ok'`；
* checkpoint 返回值满足要求；
* 备份和清单哈希一致；
* 可用磁盘空间充足；
* 目标指纹与 Dry-run 一致；
* 无未解决的 Automation、Job、云端或路径冲突。

#### 3.10.2 删除后校验

* 每个修改数据库再次执行 `quick_check`；
* `foreign_key_check` 返回零行，而不是只确认语句执行成功；
* 目标 Thread ID 在执行计划要求清理的来源中均不存在；
* 未选线程的控制样本、总量变化和关键索引满足预期；
* JSON/JSONL 可以重新解析；
* 隔离区内容与清单一致；
* 报告中的实际修改集合与 Dry-run 差异为零。

重新启动 Codex 后的侧边栏观察属于人工验收步骤，不能替代本地数据校验。

#### 3.10.3 VACUUM

`VACUUM` 不属于删除事务，也不作为删除成功的必要条件。它可能耗时、占用额外磁盘空间且无法随前述事务回滚。

只有在操作已经 `COMPLETED` 后，用户才能从独立菜单选择空间维护；执行前重新检查空间、进程和数据库健康状态。

## 6. 验证与验收方案

### 6.1 单元测试

必须覆盖：

* 序号、列表、区间、重复项和非法输入；
* 全角数字、全角逗号、顿号、全角/长短横线、波浪线和 Unicode 空格的选择语法规范化；
* 选择输入允许规范化，但删除确认短语不得被规范化；
* UUID 与本地来源验证；
* Windows 路径规范化、UNC、长路径、大小写和目录边界；
* symlink、junction、reparse point 与越界删除阻断；
* 状态分类真值表，确保分类互斥；
* JSON/JSONL 精确修改与差异输出；
* manifest 生成、哈希校验和状态机迁移；
* 未知结构的只读降级；
* 动态确认短语和过期 `scan_id` 阻断。

### 6.2 集成测试

使用脱敏夹具覆盖：

* 两套状态库与日志库同时存在；
* 只有其中一套数据库存在；
* WAL/SHM 存在、为空、繁忙和 checkpoint 不完整；
* `Connection.backup()` 在 WAL 存在时生成独立可读快照，并通过源库、快照和恢复后三次校验；
* sidecar 哈希记录、旧 WAL 隔离和恢复后不误重放；
* 只读锁持续时间短于和长于 5 秒时的等待、超时、重试与 `TEMPORARILY_BUSY` 降级；
* 表或列新增、缺失和迁移版本不匹配；
* 健康会话、catalog lag、幽灵、正文断头、孤立候选和冲突对象；
* 本地与云端相同 Thread ID 形态；
* `project_id` 为空；
* Automation、Job、spawn edge 和 artifact 引用；
* JSON 损坏、JSONL 单行损坏、权限不足和磁盘空间不足；
* `.codex` 根为 Junction、逻辑盘符与实际卷不同、多个源卷及同卷隔离目录不可写；
* 同卷重命名成功、跨卷错误阻断、目标占用以及禁止退化为复制后删除；
* 数百或数千会话下的分页、筛选与性能。

### 6.3 故障注入与恢复测试

在以下每个阶段注入异常或模拟进程终止：

* 备份开始前；
* 备份完成一半；
* 第一个数据库提交后；
* 多个数据库部分提交后；
* 文本状态替换后；
* 文件隔离后；
* 验证过程中；
* 恢复过程中。

每种情况都必须证明：

* 新操作被阻止；
* 未完成操作可被识别；
* 可以恢复到一致状态，或明确进入需要人工处理的状态；
* 备份不会被自动删除；
* 未选中的会话与项目保持不变。

### 6.4 验收门槛

1. 只读模式不得主动修改 Codex 数据文件。
2. 未知结构、云端来源、活动对象和证据冲突必须 100% 阻断写入。
3. 所有支持的测试夹具分类结果与预期一致；不使用“现实环境 100% 准确”作为不可验证指标。
4. Dry-run 与实际修改集合必须一致，发现差异即中止。
5. 所有修改对象都有清单、备份或隔离恢复路径。
6. 故障注入测试全部通过后，才能启用正式删除菜单。
7. 删除后本地校验通过，并由用户重新打开 Codex 完成人工界面验收。
8. 每个 SQLite 快照都能在无源 WAL/SHM 的情况下独立打开并通过 `quick_check`。
9. 隔离移动的源与目标卷标识必须一致；不同卷时必须在首个写操作前阻断。
10. 持续锁超过只读等待预算时，扫描必须可恢复地降级，不能崩溃或生成删除计划。

## 7. 风险、限制与非目标

1. Codex 内部数据库属于持续演进的数据结构，应用升级可能立即使写入适配器失效。
2. 工具只保证受支持版本下的本地一致性，不承诺服务端删除。
3. SQLite 完整备份会包含未选择对象的部分数据，需要明确隐私与保留政策。
4. SSD、文件系统快照或同步软件可能保留旧数据，本方案不提供法证级安全擦除。
5. 本方案不扫描其他 Windows 用户目录、注册表、浏览器缓存或远端主机。
6. 本方案不删除、移动或修改项目源码。
7. `config.toml` 标准库读取在 Python 版本上存在差异，标准库也没有保留格式的 TOML 写入器，因此写入能力必须单独解决，不能混入首期线程清理。

## 8. 本次规划调整备注

**调整日期**：2026-09-03  
**调整性质**：根据首次方案审查结果进行安全性与可实施性修订；仅修改规划文档，尚未实施代码。

| 调整项 | 原方案问题 | 本次调整内容与原因 |
| :--- | :--- | :--- |
| 作用范围 | 使用“全机所有本地项目”容易被理解为所有用户和远端数据 | 明确限定为当前 Windows 用户当前 `.codex`，并补充无法证明服务端删除的边界 |
| 进程守门 | 启动即拦截导致只读扫描也要退出；`taskkill /F` 有未保存数据风险 | 改为删除阶段才守门，首期禁用强杀，默认要求正常退出和有界轮询 |
| WAL 处理 | `PASSIVE` checkpoint 被描述为一定完整刷盘 | 要求读取 checkpoint 返回值；busy 或未完成即停止，覆盖全部实际 WAL 数据库 |
| 会话分类 | 四象限条件存在交叉，幽灵与正文断头可能同时命中 | 改为互斥多状态模型，增加云端、活动、catalog lag 和未知冲突状态 |
| 幽灵判定 | `missing_candidate` 和单次缺失证据不足以授权批量删除 | 降为辅助信号，并要求稳定复扫、时间阈值和完整负证据 |
| 存储清单 | 原方案只描述单套 state/log，备份未覆盖所有修改对象 | 纳入两套状态库、两套日志库、sidecar、辅助库、文本状态和物理对象 |
| 数据库兼容 | 固定 SQL 无法覆盖持续新增的线程引用表 | 增加迁移版本、结构指纹、版本适配器和未知结构只读降级 |
| 原子事务 | 多个数据库和文件系统无法由一个 SQLite 事务共同回滚 | 改为分库事务、操作状态机、完整备份、文件隔离和补偿恢复 |
| 备份完整性 | 固定备份清单与实际 mutation set 不一致 | 改为先生成修改集合，再为每个对象绑定备份或恢复策略 |
| 备份隐私 | 在工程目录保存全库备份可能进入 Git 或同步盘 | 默认规划到 `%LOCALAPPDATA%` 的受限目录，并增加保留期、空间和隐私提示 |
| 项目映射 | 路径小写和 `project_id` 不足以覆盖空值、嵌套根与 worktree | 增加完整路径边界、最长根、歧义状态和 reparse point 防护 |
| 选择稳定性 | 菜单序号在重新扫描后可能指向不同对象 | 绑定 `scan_id + thread_id + 目标指纹`，执行前变化即废弃计划 |
| Automation/Job | 删除会话时直接删除 Automation 属于额外用户意图 | Automation 本体默认阻断并单独确认，同时纳入 Job 等引用审计 |
| 全局 JSON | 泛化递归删除可能误删未知结构 | 改为已知 JSON 路径白名单、前后差异和原子替换 |
| `config.toml` | Python 3.10 与 TOML 读取能力不一致，标准库无保格式写入器 | 从首期移除，作为后续独立选项设计 |
| `VACUUM` | 不可回滚、耗时且可能需要大量额外空间 | 移出删除流程，改为操作完成后的独立可选维护 |
| 验收 | 原方案主要依赖人工场景，缺少结构升级与崩溃恢复测试 | 增加单元、集成、故障注入、脱敏夹具和明确质量门槛 |
| 旧入口 | “全部保留”与“唯一入口”目标冲突，且遗漏 `sidebar_ghost_targets.json` | 补全保留清单，并规划验收后弃用旧执行入口、最终统一到一个引擎 |

本次修订保留了原方案的统一控制台、多源扫描、人工确认、备份和执行后验证方向，但将高风险能力拆分为后续阶段，优先保证首期只读扫描、Dry-run、精确线程清理和故障恢复能够被独立验证。

### 8.1 第二轮实施边界补强

**调整日期**：2026-09-03  
**判断结论**：提出的四项细节均合理，已纳入规划；同时收紧了其中可能造成过度承诺或新安全风险的表述。

| 补强项 | 合理性判断 | 纳入规划的实施规则 |
| :--- | :--- | :--- |
| SQLite `Connection.backup()` | 合理，优于把主库、WAL 和 SHM 的普通文件复制组合作为默认恢复基线 | checkpoint 和源库检查通过后，逐库使用 `backup()`；快照独立 `quick_check`、刷新落盘并计算哈希；sidecar 只作诊断清点，恢复时隔离旧 sidecar，避免 WAL 错误重放 |
| Junction 与跨卷隔离 | 合理，跨卷 `rename` 不能提供所需的同卷重命名语义 | 区分“可跨卷复制的备份目录”和“必须同卷的隔离目录”；解析实际物理卷，每卷建立隔离根；禁止自动退化为复制后删除，也不默认写入盘符根目录 |
| 只读扫描 `busy_timeout` | 合理，能显著减少短暂锁造成的浏览失败 | 统一 `timeout=5.0`、`busy_timeout=5000` 和 `query_only=ON`；明确这是最长约 5 秒的有界等待，持续锁仍需捕获并降级为 `TEMPORARILY_BUSY` |
| 中文输入法全角字符 | 合理，能减少序号选择的无效重输 | 使用 NFKC 加显式字符映射统一全角数字、逗号、顿号、横线、波浪线和空格；规范化后严格校验并回显结果；永久删除确认短语不做相同规范化 |

需要特别保留的限定：

1. `Connection.backup()` 可以产生事务一致且不依赖源 WAL 的独立快照，但不能用“100% 完美”描述；源损坏、磁盘故障和跨库时间点差异仍需校验及恢复设计。
2. 同卷重命名避免了常规跨卷复制再删除，但不排除占用、ACL、杀毒软件和 I/O 错误。
3. `busy_timeout` 是有界阻塞等待，不是非阻塞缓冲，也不能彻底杜绝锁异常。
4. 全角容错只服务于菜单选择，不能弱化破坏性操作的精确确认机制。
