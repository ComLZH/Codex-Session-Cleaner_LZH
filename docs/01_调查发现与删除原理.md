# 调查发现与删除原理

## 1. 需求背景

目标是彻底清理本地项目在 Codex 中留下的记录，而不是简单归档，也不是删除项目源码。

官方 OpenAI 文档目前明确说明了项目、任务、归档和恢复，但没有公开 Codex 桌面任务的永久删除接口：<https://learn.chatgpt.com/docs/projects>。

因此，本工具处理的是本机 Codex 存储。它不能证明 OpenAI 未公开的服务端副本已经物理删除。

## 2. 为什么手工删除 rollout 文件仍会看到记录

一次 Codex 任务并不只对应一个 JSONL 文件。项目或任务信息还可能存在于：

- `.codex/session_index.jsonl`
- `.codex/cap_sid`
- `.codex/state_5.sqlite`
- `.codex/sqlite/state_5.sqlite`
- `.codex/thread_history_1.sqlite`
- 两份 `.codex/logs_2.sqlite`
- `.codex/thread-writer-locks`
- `.codex/visualizations`

如果只删除 `.codex/sessions` 下的 rollout 文件，SQLite 状态行和 `session_index.jsonl` 仍然可能让任务继续显示。

## 3. 典型实例与幽灵条目成因

在很多开发项目中，历史旧任务的 rollout 文件可能已经被手动删除或丢失，但 `session_index.jsonl`、两套 `state_5.sqlite` 以及桌面端的 `codex-dev.db` 仍保留目录索引。这是“文件已删、Codex 中仍有记录（点击报错文件不存在）”的直接实例。

## 4. 数据库关系

只读扫描确认：

- `state_5.sqlite/threads` 保存任务主体和 rollout 路径。
- `projects`、`project_roots`、`project_idempotency_keys` 保存项目、目录和外部 ID映射。
- `thread_history_1.sqlite` 保存任务轮次、消息项目和投影位置。
- `logs_2.sqlite/logs` 保存任务运行日志，其中可能再次包含项目路径或任务 ID。
- `cap_sid` 保存工作目录和 visualization 可写目录的权限 SID映射。

项目源码和 Codex 记录是两类不同数据。本工具只操作用户目录下的 `.codex`，绝对不会进入项目代码目录删除源码。

## 5. 本工具的处理策略

工具采用动态发现与证据模型，按会话唯一 `thread_id` 和项目路径进行识别。执行删除时：

1. 检查目标任务锁，发现 Codex 仍在运行便拒绝执行。
2. 建立 Connection.backup() 一致性数据库冷备份与 SHA-256 清单。
3. 在 SQLite 事务中删除精确命中的任务、项目、历史和日志行。
4. 定向过滤文本索引，不删除整个共享索引文件。
5. 将物理 rollout、锁和 visualization 移入同卷隔离区 (Quarantine)。
6. 重新审计并生成 JSON 报告。
